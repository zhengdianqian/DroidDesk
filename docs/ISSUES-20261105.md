## a) APK 启停慢（`wait_gui` 轮询问题）

**复现步骤**
1. 装 `chroot/dist/Ubuntu-Container-v1.3.apk`；
2. root shell 起代理：`su -c 'sh /data/local/tmp/ubuntu-agent.sh start'`；
3. 点「停止容器」→ 计时；再点「启动容器（图形）」→ 计时。

**期望**：按钮 2~3 秒内返回结果，桌面在后台继续起。

**实际**
- 关闭图形 37.3 s、停止容器 58.5~60.7 s、打开图形约 45~50 s；
- 期间按钮一直 busy（`busy=true`），曾出现卡住不回调。

**根因（已定位）**
1. `wait_gui()` 每轮都调 `ubuntu-status.sh`，该脚本遍历 `/proc/*/root` 并在 chroot 内跑 `xdpyinfo`，**约 12 s/次**，
   100 轮上限 → 最坏 20 分钟；
2. 代理 `nc -lk` 串行处理连接，长动作把后续 `status` 请求一起堵住；
3. `ubuntu-start.sh --mount-only` 里 `dbus-daemon --system --fork` 继承了 socket fd 0，
   客户端永远等不到 EOF → 必须文件重定向 + `</dev/null`；
4. APK 侧没有看门狗，动作线程抛异常/超时后按钮停在 busy。

**已试/已改（本次提交）**
- `wait_gui()`：改为 `sleep 0.2` 轮询 + **20 s 硬上限**，只查 `ps -A -o NAME` 与 X socket，不再跑 status 脚本；
  超时输出「图形仍在启动中（已超 20s，后台继续）」，按钮立刻返回；
- 代理协议以 `ELAPSED <ms>` 结尾，APK 见到即返回，不依赖对端关闭连接；
- 所有动作走统一 `action()`，`try/catch/finally` 保证一定回调 `finish()`（看门狗）；
- 脚本调用统一 `</dev/null >log 2>&1`，避免后台守护进程继承 socket fd；
- `stop` 后用轻量 `mounts` 轮询等挂载真正归零再回报，避免误报失败。

**下一步建议**
- 重新构建并复测四个按钮，目标：停止 < 5 s、启动（图形）< 20 s 返回，桌面继续后台启动；
- 若仍需更快：代理改成 fork-per-connection（busybox `nc -lk -e` 已 fork，但长动作会占住父进程等待），
  或把 `status` 轻量化（缓存 `/proc` 扫描结果、`xdpyinfo` 只在刷新时跑）。

  `screenshots/desktop-dock-gesture.png`）。

**已试方案**
- 定位到 Termux:X11 偏好 `showAdditionalKbd/additionalKbdVisible/adjustHeightForEK`；
  `ubuntu-start.sh --gui` 启动前自动改这三项为 false 并 `restorecon`（需 root 改 `/data/data/com.termux.x11/shared_prefs/`）；
- 另发现 `startplasma-x11` 会被 `kscreenlocker_greet` 全屏锁住，看起来像"桌面丢了"；
  已在 `start-desktop-x11.sh` 写入 `kscreenlockerrc`（`Autolock=false` / `LockOnStartup=false`）。

**遗留**

2. 顶部 KDE 面板与 Android 状态栏在视觉上仍有 ~40px 重叠区，目前靠"X 屏幕 = 可用高度"规避，
   若用户要求悬浮式沉浸全屏，需要在 Termux:X11 侧做 `fitsSystemWindows` 处理（第三方 APK，改不了）；
3. 备选方案（未实施）：在我们自己的 APK 里内嵌 `SurfaceView` + `WindowInsets` 显示 X 画面，
   可完全控制 insets，但需要接 Termux:X11 的 server socket，工作量大。

**下一步建议**：先复测锁屏修复；若用户只关心"Dock 可见 + 手势可用"，当前已达标；否则再做内嵌显示。

## c) 三方软件打不开（7 项排查结论）

**复现步骤**：chroot 内点 Chromium / WeChat / Feishu 等 `.desktop` → 无反应。

**根因（已确认）**
1. `/data` 挂载带 **nosuid**；
2. 内核**无 user namespace**（`unshare -U` → `EINVAL`）；
   → Chromium/Electron 的 setuid 沙箱与 userns 沙箱都不可用，进程在沙箱初始化阶段直接退出（GUI 无提示）。

**七项逐条**
| # | 检查项 | 结论 | 处理 |
|---|---|---|---|
| 1 | `/dev/shm` | ❌ 原本未独立挂载 | ✅ 已加 `tmpfs size=2G,mode=1777` |
| 2 | dbus | ❌ 无 system bus | ✅ `dbus-daemon --system --fork`；`dbus-run-session` 包住 startplasma |
| 3 | `XDG_RUNTIME_DIR` | ❌ 未设置 | ✅ `/run/user/1000`，700 |
| 4 | `ldd` / stderr | 无缺失依赖；chromium 日志有 `EGL glXGetMscRateOML failed`、`XFree86-VidModeExtension missing`（非致命） | ✅ `chromium --no-sandbox` 可出窗口 |
| 5 | SELinux avc | ✅ 无拒绝 | 无操作 |
| 6 | `/proc` `/sys` `/dev/pts` | `/dev/pts` 缺失（bind `/dev` 不带子挂载） | ✅ 单独挂 `devpts gid=5,mode=620,ptmxmode=666` |
| 7 | AppImage / `/dev/fuse` | ❌ 无 `fusermount`；`/dev/fuse` 存在但 600 root | 只能用 `--appimage-extract` 解包后直接跑 |

**已修**
- `fix-thirdparty.sh`：扫描 `.desktop`，命中 Chromium/Electron 特征（`chrome-sandbox`、`resources.pak`、
  `icudtl.dat`、目录名/文件名关键字）后给 `Exec=` 追加 `--no-sandbox`，共改 11 处，原文件留 `.orig`；
- 写 `/etc/chromium-browser/default`：`CHROMIUM_FLAGS="--no-sandbox"`；
- 回滚脚本 `restore-thirdparty.sh`。

**遗留 / 待办**
1. **dbus 重启 bug**：`start_system_dbus` 只判断 `/run/dbus/system_bus_socket` 是否存在，
   容器停了再起时 socket 是**残留文件**，会跳过启动 → 应改成按进程判断（`pgrep -x dbus-daemon`）；
2. 未逐个验证 WeChat / Feishu / dingtalk 的真实启动（只确认 `.desktop` 已被改写）；
3. flatpak 未验证（chroot 无 systemd，大概率不可用）；
4. 依赖 `/dev/fuse` 的 AppImage 明确不支持，需在文档里对用户说明。

**下一步建议**：修 dbus 判断逻辑 → 起容器后 `ps -A | grep dbus` 确认 → 再逐个点三方程序并截图。

## e) 临时 root 掉后如何恢复

**现象**：KSU 临时 root 失效后，`/system/bin/su` 消失，APK 状态区显示「ROOT 不可用」，
root 代理也随进程消失。

**复现步骤**：重启设备（或 KSU 失效）→ 打开 APK → 状态区提示先恢复 ROOT。

**恢复流程**
1. 重新获取临时 root（RPPROOT / KSU 管理器内重新激活，按用户既有方式）；
2. 校验：`su -c id` 输出 `uid=0 ... context=u:r:ksu:s0`；
3. 重启代理：`su -c 'sh /data/local/tmp/ubuntu-agent.sh start'`；
4. 打开 APK → 点「刷新状态」→ 看到「可用 (root 代理)」即可操作；
5. 容器若需重建：APK 点「启动容器（图形）」，或命令行 `ubuntu-start.sh --force --gui`。

**期望**：APK 在无 root 时**明确提示**而不是静默失败（已实现，v1.3 状态区 + 结果区都会提示）。

**下一步建议**：如果用户接受，把 `ubuntu-agent.sh start` 放进 `/data/adb/service.d/` 实现开机自启
（本次遵守"不动 KSU"约束，未写入）。

## 附：需要用户手动授予的权限（本应用不会自行修改任何权限设置）

| 权限 | 用途 | 当前状态 | 手动操作路径 |
|---|---|---|---|
| KSU root 授权（`com.trae.ubuntu.container`） | 直接 `su -c` 通道（可选，有代理时不需要） | ❌ 未授权 | KSU 管理器 → 超级用户 → 授权本应用 |
| `INTERNET`（普通权限） | 连接 `127.0.0.1:47123` 代理 | ✅ 已声明，自动授予 | 无需操作 |
| 无 `SYSTEM_ALERT_WINDOW` / `REQUEST_INSTALL_PACKAGES` / 存储权限需求 | — | — | 本 APK 未申请 |

> 说明：KSU 3.3.0 「越狱模式」对未授权应用隐藏 `su`，且该应用不在 `/data/adb/ksu/.allowlist`，
> 所以 `exec("/system/bin/su")` 直接 `ENOENT`。这是 root 授权问题，不是 APK 权限问题；
> 在用户授权前，APK 统一走 root 代理。
